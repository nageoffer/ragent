# Agent 记忆行为与机制回归

[返回回归与测评总览](../README.md)

验证已启动 Ragent 服务的工具结果裁剪、会话摘要和长期记忆。复用 `resources/initializer/common` 的配置、HTTP 与 JDBC 客户端，使用 Java 17 CLI，不启动 Spring。

本套件的编译缓存与运行日志放在 `artifacts/`，由仓库根 `.gitignore` 忽略。CLI 报告输出到控制台，需要留存时重定向到 `artifacts/<本次运行目录>/`。

| 入口 | 用途 | 数据操作 |
| --- | --- | --- |
| `AgentMemoryRegressionMain` | 按剧本验证多轮和跨会话记忆 | 通过真实聊天生成会话、消息及可能的长期记忆；直接读库观测 |
| `AgentMemoryMechanismMain` | 验证版本校验、水位、并发、合并和容量 | 会直接写测试状态并执行清理，范围及限制见下方「机制回归」 |
| `AgentMemoryProbeMain` | 排查已有会话 | 只读状态，不发起聊天 |

定量指标和 A/B 比较见 [Agent 记忆测评](../agent-memory-evaluation/README.md)；独立账号的真实缺陷复现与证据导出见 [记忆问题审计](../agent-memory-audit/README.md)。本页保留原有历史观测及代码推断，不表示文档迁移时重新完成了这些测试。

## 行为回归

### 它验证什么

| 层 | 机制 | 剧本怎么验 | 现状 |
| --- | --- | --- | --- |
| 短期 | 工具结果清理（`AgentContextTrimmer`） | t01 植入知识库里查不到的锚点，t02~t07 把上下文撑大到触发清理，t08 要求原样复述锚点 | 已实现，硬断言 |
| 中期 | 安全前缀压缩 + 会话摘要（`AgentContextCompactor`） | t09 问只在 t02 说过一次的工位号；t14 问 t10 更正过的资产编号。两轮都**不许重新检索** | 已实现，硬断言 |
| 长期 | 跨会话用户事实（`AgentUserMemoryMiddleware` + 抽取管道） | t15 另开一条会话直接问工号 | 已实现，硬断言 |

三层都已落地，`MemoryTurnScript.IMPLEMENTED_TIERS` 三个值齐了，剧本里没有 PENDING 轮次。
往后新增记忆层时，先在 `tier` 上写新值再实现，答不出只记 PENDING，实现之后加进 `IMPLEMENTED_TIERS`
就自动转成硬断言——这套剧本同时也是每一层的验收用例。

剧本验的是**回答里记不记得**。长期记忆还有一整套只能从库上看的管道行为（并发、水位、容量），
那些走另一个 CLI，见下文「机制回归」。

两条中期断言各验一件事，都建立在同一个前提上——**被问的事实只说过一次，之后再没被复述**，
所以它一旦被压缩吃掉，答对就只可能来自摘要：

- **t09（保真）**：工位号 `B3-1207` 只在 t02 出现过，知识库里查不到、问题里也没带。答对说明用户原话
  被摘要 verbatim 带过来了。同轮保留 `forbid-tool`：又调一次 `search_knowledge` 就是 FAIL——那说明摘要
  没把工具结论带过来，模型只能回头重查。
- **t14（取新）**：t01 说资产编号是 `NB-2049`，t10 更正为 `NB-3160`。答旧值即 FAIL——那说明第一代摘要
  里的旧值被逐代抄了下来，「与新记录冲突时以新记录为准」没有真的生效。

关键词式断言只有在这个形态下才站得住。反例是本剧本早先那版 t09（`归还|资产|交接`）：三个词问题里就带着，
模型凭空编一句也能 PASS。

### 两层记忆按水位分工，不是二选一

**超过预算的 50% 时裁工具结果**（换成占位、不删消息、不调模型），**80% 起才压缩**（真删早期原文、要调一次
模型、有损）。裁剪只要求存在白名单内、保护窗口外且替换后净缩短的候选，不再要求回收量达到当前总量的
20%。低破坏的手段永远先动手。

**裁剪本身不能给上下文总量设上界。** 它只改写 `tool_result`，能省下的量受它在上下文里的占比限制，
而那是**语料属性不是常量**。下面保留的是 08-25 使用旧版 20% 最小回收门槛、关掉压缩跑满 15 轮的数据；
它不代表删除门槛后的效果，新规则尚未重跑真实模型回归。该次末轮 30575 字符的构成是：

| 块类型 | 字符 | 占比 | 裁剪能动吗 |
| --- | --- | --- | --- |
| `text`（用户话 + 助手回答） | 13823 | 45.2% | ✗ |
| `thinking` | 8039 | 26.3% | ✗ 明令永不清理 |
| `tool_result` | 6851 | 22.4% | ✓ 但 11/26 块已是占位 |
| `tool_use` | 1862 | 6.1% | ✗ |

旧规则里，可回收量还得达到当前总量的 20%，受保护的结果与占位又不能贡献回收量。该次裁剪在 t04/t06
各成功一次之后连续九轮没有再发生，上下文一路涨到预算的 **3.8 倍**。没有逐轮核对候选，不能把后续停滞
全部归因于比例门槛；这组数据能说明的是旧规则下裁剪没有控制住总量。光 `thinking` 一项就比整个工具结果存量还大。

**这条直接决定 `summary-enabled: false` 的性质**：它是摘要模型不可用时的运维出口，但**不是有界的降级**
——关掉之后没有任何东西摁得住水位，一直涨到模型真实窗口报 overflow，而撑爆的那份上下文会被应用侧
补存下来、下一轮重问会带着同一份上下文重来（见下文，代码推断未实测）。
工具吐大块的语料（一次检索几万字符）裁剪才是主力层，那种形态下这张表会反过来。

代价说在前面：压缩的素材因此可能已经被裁过。占位里带着当时的检索问题，而 `search_knowledge` 返回的
本就是合成后的答案、助手回答里还会复述一遍，所以摘要的 `## 工具与发现` 一节会变薄但不至于空。这是这版
设计明知并接受的取舍，不是 bug。

**旧规则下两层同时开启的那跑**（8000 预算、白名单原样留着 `search_knowledge`，15 轮），压缩发生了 4 次，
裁剪只成功了 1 次。那时既保护最近两个循环，又要求回收量达到当前总量 20%；这些次数不能外推到新规则。
现在清空 `evictable-tools` 仍可**让报告只观测压缩这一层**，避免裁剪先降低水位影响压缩覆盖度；两层都开时
究竟先后触发多少次，需重跑确认。

**两层防的都是跨轮慢涨，单轮 ReAct 内部顶穿上下文不在射程内。** 一轮里的循环全受保护，那时裁剪裁不出
字节来，压缩也只在轮次静默点判。

`context-window-chars` 是**会话上下文工程预算**，不是模型物理上限的字符换算值，所以「预算离标称窗口还差
多少」不能拿来当安全余量算。能用来裁决的只有实测——本机 12 条会话、16 轮、25 次模型调用，读
`t_agent_state.payload->'context'` 里供应商回填的 `usage`，字符数按 `AgentContextChars` 口径在 SQL 侧复算：

| 量 | 实测 |
| --- | --- |
| 单轮上下文增量峰值 | 8,810 字符 |
| 单次 ReAct 循环增量峰值 | 5,794 字符 / 3,667 token |
| 单块 `tool_result` | max 3,271 / p90 2,781 / 均值 725 |
| 单轮模型调用数峰值 | 5 次（上限 `agent.max-iters: 10`） |
| 固定开销（人设 + 工具 schema） | 2,855 token |
| 语料折算 | 约 1.6 字符/token |

按峰值循环 × `max-iters: 10` 外推，单轮上界约 5.8 万字符，远小于生产预算给两道门留出的空间。**这条外推只
对 `search_knowledge` 成立**：`KnowledgeSearchFacade.search()` 返回的是再合成一次的答案（`llmService.chat`），
原始 chunk 根本进不了 Agent 上下文，产出被答案模型自己的输出上限卡着，与 `rag.search.default-top-k` 无关。
**输出不受限的 MCP 工具没有这道界，那条路径是「尚未量化验证的已知风险」**——样本里的 `leave_query` 最大只有
193 字符，但那是这一个工具的观测值，约束不了整个 MCP 工具集。样本量也撑不起 P99：25 次调用、单轮最多 5 次
循环，能报的只有 max。

**真撞上之后不是「下一轮自愈」，是水位被持久化下来**（下一轮开头会先试一次压缩——它在 `onReasoning`
里、模型调用之前跑；压缩也救不回来时就会再失败一次。这一段是代码推断，没实测过）。框架侧确实
不存：`saveStateToSession` 只挂在成功路径的 `flatMap` 上（`ReActAgent.java:1021`），异常走
`AgentBase.createErrorHandler` 直接 `Mono.error` 重抛。但**应用侧补了存盘**——`AgentChatServiceImpl`
的释放钩子在 `runHandle.isStateSaveRequired()` 时补调一次 `agent.saveAgentState`（为的是别丢已执行的
工具结果），`AgentStreamEventBridge.onError` 也会把消息按 `INTERRUPTED` 落进 `t_agent_message`。所以
失败轮的上下文增量是**留得住的**：下一轮 `activateSlotForContext` 从库里重新加载，读到的是已经撑爆的
那一份，再问一次同样超窗。水位常量救不了这个，只有摘要这一层能。

> 本节早先写作「那一轮整个不落库，会话不会因此膨胀」，那是只核了 `agentscope-core` 2.0.2、没算上应用侧
> 补存盘的结论，已随取消/中断那批改动失效。旧说法把后果说轻了：实际是卡住，不是丢一轮。

### 前置条件

- JDK 17，`java` 与 `javac` 都在 PATH；
- RagentAI、PostgreSQL 已启动，服务读的是 `bootstrap/src/main/resources/application.yaml`；
- `ragent.engine.type=agent`——`workflow` 档位走的是 RAG 编排管线，根本没有 Agent 记忆；
- **`enterprise-knowledge-base` 模板已经初始化过**。中间 6 轮撑量问题取自该模板，库里没内容就检索
  不到东西，上下文涨不起来，清理永远不触发，整场跑完只会得到一堆 UNCOVERED；
- 账号 `admin/admin` 可登录，在 `regression.properties` 里改。

### 跑一次

在项目根目录执行：

```bash
mkdir -p resources/regression/agent-memory/artifacts/classes

javac -encoding UTF-8 \
  -d resources/regression/agent-memory/artifacts/classes \
  resources/initializer/common/*.java \
  resources/regression/agent-memory/*.java

java -cp resources/regression/agent-memory/artifacts/classes \
  com.nageoffer.ai.ragent.initializer.AgentMemoryRegressionMain \
  --suite-dir resources/regression/agent-memory
```

15 轮全是真实模型调用，通常要跑十分钟上下。加 `--verbose` 会顺带打印每轮回答的前 400 字——判断模型
是真记得还是蒙对了关键词，只能靠人看这一段。

看到 `[regression] SUCCESS` 才算通过。任何一条 FAIL 都会以非零状态退出。

改过 `resources/regression/**` 或 `resources/initializer/common/**` 之后，编译这一步必须重跑。

### 怎么读报告

报告有四段：

**逐轮观测**——每轮的回答字数、上下文消息数、工具循环数、≈字符数、tool_result 块数、已清理块数、
摘要消息数、payload 字节。`摘要` 列从 0 变 1 的那一轮就是压缩落点，同一轮的 `消息数` 与 `≈字符`
会同时掉下来——这是压缩唯一的、可自动检出的痕迹。`≈字符` 是在 SQL 侧按 `AgentContextChars` 的口径
复算的，其中 `tool_use` 的入参服务端算的是 `Map.toString()` 长度、这里算 JSON 文本长度，**所以它是
近似值**。要精确数字请看服务端日志的 `上下文裁剪完成` / `上下文压缩完成`。

**阈值校准**——七个指标。**能回填的只有 `context-window-chars` 一个数**，其余派生比例是编译期常量，
所以这张表读的不是「该调哪个键」，而是「这个数说明什么」：

| 指标 | 这个数说明什么 |
| --- | --- |
| ① tool_result 体量分布 | 单块多大。存量包含受保护、非白名单及已清理块，不等于可回收量；超过裁剪水位后，有符合条件且替换后净缩短的候选就裁 |
| ② 上下文总量峰值 | 峰值离两道门有多远。离得太远就是本次没覆盖到，该动的是预算或撑量轮 |
| ③ 输入 token 峰值 | 供应商回填的权威读数。**不要拿它去除②算字符/token**：②只算会话上下文，③含人设与工具 schema（实测固定开销 2855 token），两个峰值还可能来自不同次调用。折算比例见下方实测表，那是**填预算时**的工作负载换算，不是运行期不变量 |
| ④ 命中缓存峰值 | 两层改写前缀可能影响缓存命中。命中下降本身不能说明裁剪不值，要结合实际费用、延迟及后续请求的输入缩短量判断 |
| ⑤ 工具循环 / thinking 块 | 保两个循环够不够用（常量 2）；thinking 块数量是它永远不被清理的证据 |
| ⑥ 压缩落点 | 保留段（预算的 20%）与峰值的关系。越过压缩门后只在找不到安全切点时跳过，即保留够量后往前再没有用户轮起点 |
| ⑦ 摘要产物 | 末轮摘要消息条数与派生出的正文上限（预算 10%，夹进 1500~6000）。摘要写得对不对只能人看，用 `AgentMemoryProbeMain` 打开末轮状态，它会把末代摘要正文整段印出来 |

**摘要长度曾经随用户轮数单调涨，那是原话免压缩的直接后果，2026-09-19 已把豁免取消。** 旧形态下
`## 用户诉求` 一节逐条 verbatim 且明令不参与再压缩，所以每多一个用户轮它就多一行：实测四代
638 → 778 → 1106 → 1285 字符，本机语料约 70 字符/用户轮。斜率本身不是问题，撞上限之后的形态才是——
当时的 `validate` 在最后一个完整 `\n## ` 边界截断（2026-09-30 起不再截；2026-10-04 起超出字数目标照收，只有被 token 上限截断才放弃），掉的是尾部小节，而一节**永不参与取舍**的正文一旦自己就超了
上限，每一代都切不出合格结构、`validate` 代代返回 null，压缩这一层整个停摆，只剩射程有限的裁剪。
按 70 字符/轮外推「八十轮才咬」站不住：增量等于用户那句话的长度，贴几段报错日志就能把 6000 填满。

现在改成**否定、条件、范围、数量与时限逐字保留，其余可改写压缩**，七个小节全部参与取舍，超长时从末节
倒着压。代价是用户原话不再逐字传代、递归压缩有漂移风险，收益是摘要有界（2026-09-19 夜 6 代回归里
`## 用户诉求` 第 4 代起逐字不再长，压缩层没有停摆；停摆的必然性只是推理，没有在旧规则下实测到）。
**这条取舍靠回归判**：跨 3~4 次实际成功压缩，看那几个约束词有没有在传代中被丢掉，只数轮次或查关键词
都不算验过。

第一版措辞在这个判据下没过：「需经 DBA 书面批准」被压成「需经批准」、「除非我明确同意才引入 MQ」掉了
条件、「并发不低于 3」掉了「否则跑不完每天 800 份」这个理由——限定词被当成可压缩的修饰语。补了一句
「限定词也是条件」并举三个改坏的例子之后重跑，六代全部逐字保住。同一轮还给摘要头加了「摘要里没有
不等于没发生过」：模型此前会把「摘要没保留」当成「事情没发生过」讲给用户，改口的旧值丢了却断言从没
改过口，比丢信息本身更危险。**改口只保留新值是新规则的既定后果**，试过用提示词让它把旧值记进
「走不通的路」，两代摘要都无视，已退回——现在的形态是模型答「变更前的原话我这边没有保留」。

**同一批还查出一个与豁免无关的老毛病：助手起草的动作被记成已经做过。** 用户让写一封给 DBA 的邮件、
助手明确输出的是草稿，摘要的 `## 当前进度` 却从第 3 代起写成「已向 DBA 发出正式配合请求」，一路传到
第 6 代——接手的模型会以为协作请求已经发出，不再提醒用户去发。没有旧版对照，不能断言是取消豁免带来的。

**这条规则第一版写成了全局约束，两跑都把摘要写坏**：`## 用户诉求` 从「一条一行」塌成一整段分号串，
「否则跑不完每天 800 份文档」这个理由两跑都掉了。全局约束区在这份提示词里是「怎么取舍」的位置，往里
加内容判断会稀释小节自己的格式要求。改成把话贴进 `## 当前进度` 与 `## 已完成` 两节后重跑：7 代零放弃，
草稿全部记成「已起草 X，未发出」，九条限制连同理由逐代保住。**同类改动照这个位置走：规则贴在它约束的
那一节里，全局区只留长度、真实性、专名三条。**

**所以摘要回归多一条定点检查**：剧本里放一轮「帮我起草一封邮件」，在它之后至少压两代，读
`## 当前进度` 与 `## 已完成`，出现「已发出 / 已提交 / 已通知」就是 FAIL。

上下文里只留得住最后一代摘要，前几代被覆盖后就没了。要看某一代到底丢了什么，查审计表：

```sql
SELECT generation, material_msg_count, material_chars, summary_chars,
       context_chars_before, context_chars_after, create_time, summary
FROM t_agent_context_compaction
WHERE conversation_id = '<会话ID>'
ORDER BY generation;
```

这张表是追加型日志，应用侧没有读路径，压缩删掉的原文只在这里留下凭据。

被**裁剪**换成占位的工具结果是另一条路：占位重建时保留了原块的 `id`，而 `t_agent_message.blocks`
里每个 tool 块都带着同源的 `toolCallId`，所以原文能精确回查。先从状态里取 id——
`AgentMemoryProbeMain` 打印的上下文里那条占位所属的 `tool_result` 块，或直接查 `t_agent_state`——
再拿它翻冷日志：

```sql
SELECT m.create_time, b->>'name' AS tool, b->>'result' AS result
FROM t_agent_message m, LATERAL jsonb_array_elements(m.blocks) b
WHERE m.conversation_id = '<会话ID>'
  AND b->>'toolCallId' = '<tool_call_id>';
```

按 `conversation_id` 收窄是必须的：`blocks` 上没有 GIN 索引，不带这个条件就是全表扫。端点不回
`toolCallId` 时该字段为空，此时只能按 `create_time` 顺着时间线找——被压缩删掉的消息也只有这一条路，
它在上下文里连块都不剩了。冷日志本身的单块上限是 `AgentStreamEventBridge.TOOL_RESULT_MAX_CHARS`
（64000 字符），比这更长的结果在冷日志里也是截断的。

**判定**——五种状态：

- `PASS` 通过；
- `FAIL` 回归，退出码非零；
- `PENDING` 该层还没实现，答不出是当前的正确行为；
- `UNEXPECTED` 没实现却命中了，需要人复核是不是走了别的路径蒙对的；
- `UNCOVERED` 本次没跑到这个分支，不算回归，但也不能算验过。

**本次会话**——主会话与新会话的 ID，拿去做单会话排查。

### 让压缩确定性地触发

服务端只有 `context-window-chars` 一个数要配，它是**会话上下文工程预算**而不是模型标称窗口的字符换算值：
人设、工具 schema、本轮输出预留都不走这份账，填数时就该先扣掉。裁剪门是它的 50%、压缩门 80%、压缩后
保留 20%，摘要正文上限同样从它派生（10%，再夹进 1500~6000 之间）。

**现在 yaml 里的有效值是 10 万字符，不是 120 万。** `AgentMemoryProperties.contextWindowChars` 的字段
默认值仍是 120 万，但 `bootstrap/src/main/resources/application.yaml` 覆盖成了 100000，是
`1cb684ed`（长期记忆那个提交）在同一个 hunk 里改的，提交说明和 yaml 注释都没给理由，数量级恰好落在
下文「把服务端预算压到 30 万以内」那套调试口径里——**很可能是调试残留，动它之前先跟人确认**。按这个值
算：裁剪门 5 万、压缩门 8 万、摘要正文上限 6000（10% 的派生值 1 万被夹回上限）、记忆块上限 1500
（0.5% 的派生值只有 500，被夹回下限）。

按 120 万那档跑，压缩门落在 96 万；实测一条十余轮会话不到七千字符，**两层一次都不会触发**，报告会给
两条 UNCOVERED，t09 与 t14 两条中期判定则会 FAIL。10 万那档门槛低了一个数量级，但七千字符照样够不着
5 万的裁剪门——**两档都得按下文调预算才验得到**。这说明的是「这次没跑到」，不是「代码坏了」——但机制
没被验过就是没被验过。

要确定性地覆盖压缩逻辑，把预算调到实测峰值附近，重启服务再跑一遍：

```yaml
agent:
  memory:
    context-window-chars: 8000  # 压缩门落在 6400，取报告里「上下文总量峰值」的 0.8 倍附近即可
    evictable-tools: [ ]        # 可选：清空后报告里只剩压缩这一层，读起来不串；不清也压得到（见上文实测）
```

改完 **必须重启进程**，配置是 `@ConfigurationProperties` 一次性绑定的。重跑后应当看到（括号里是
2026-08-25 那跑的实测值，白名单当时没清、两层都在）：

- 校准表 ⑦ 印的「摘要正文上限」在这个预算下是 1500：10% 的派生值只有 800，被夹回下限。**它会比调预算
  之前小一截**（10 万那档夹到上限 6000），这正是派生生效的样子；两档都印 1500 才说明没绑上；
- 逐轮观测里 `摘要` 从 0 变 1，同一轮 `消息数` 明显掉下来。**`≈字符` 不一定跟着掉**——快照是那轮跑完
  之后取的，压缩发生在轮首，新一轮自己加的字符会把降幅盖掉（实测 t04：消息数 10→9，字符 6595→6780
  反而涨了）。要看压缩本身的量只能看日志 `上下文压缩完成` 那行的 `总字符: A -> B`；
- `t_agent_context_compaction` 里该会话有三到四行（实测 4 行：素材 6/8/8/12 条，
  上下文 6648→3416、9598→3700、8300→3209、9043→4169，单次回收 55%~64%）；
- `判定` 里 `会话摘要资产已生成` 与 t09 / t14 两条中期召回都转成 PASS；
- **t09 / t14 未重查 search_knowledge** 是 PASS——摘要把结论带过来了，模型不必回头重查；
- **锚点在状态里始终可寻回** 仍然是 PASS——压缩会真删早期原文，锚点届时活在摘要里，两头都丢才是越界；
- **上下文里没有孤儿 tool_use / tool_result** 仍然是 PASS——压缩只在用户轮起点切，切点前后各自配得齐，
  出现孤儿会让 DeepSeek 直接返回 400。

### 单独验证裁剪

将预算调低，让裁剪检查时的上下文超过预算的一半，并准备白名单内、保护窗口外的工具结果。只验证裁剪时可关闭摘要，避免压缩先移除待验证的旧消息：

```yaml
agent:
  memory:
    context-window-chars: 8000  # 裁剪门落在 4000
    summary-enabled: false      # 可选：关掉压缩层，让这一跑只观测裁剪
```

超过裁剪水位之后，只要存在白名单内、保护窗口外且替换后净缩短的工具结果，就会裁剪。
如果 `已清理` 仍为 0，先结合日志确认是否裁过又被压缩移除，再核对裁剪检查时的水位、工具白名单及保护窗口。
快照是在轮末取的，峰值过门不代表裁剪检查时已经过门；本轮、未完成循环和最近两个历史循环也仍受保护。
报告里的 `工具结果存量` 包含这些不能裁的块，不能直接当成可回收量。

关闭摘要单独验证时，应当看到 `已清理` 从 0 变成正数且只增不减，`工具结果裁剪已实际触发` 转 PASS，
`锚点原文始终留在上下文里` 仍是 PASS——裁剪只改写工具结果，从不删消息、也不碰用户说过的话。

**关掉 `summary-enabled` 之后 t09 / t14 仍然应当 PASS，别把它们的 FAIL 当成预期代价。** 这两轮问的
`B3-1207` 与 `NB-3160` 都出自**用户消息**（t02 / t10），而裁剪只改写 `tool_result`；压缩一关就没有任何东西
删得掉用户原话，模型是直接从原始历史里读到的。**这时候 FAIL 才是真信号**——说明有别的东西在吃用户文本。
真正会变的只有 `会话摘要资产已生成`：没有摘要消息，它转 **UNCOVERED**（不是 FAIL，退出码仍为 0）。

旧规则实测形态（08-25，8000 预算 / 15 轮）：**只在 t04 与 t06 各成功一次**（`14728 → 11177`，7 块；
`22048 → 16671`，4 块），随后 t07~t14 连续九轮全部空转。`已清理` 的轨迹是 `0 → 7 → 11` 然后平了。
判定只要求 `已清理 > 0`，裁一次就够；删除最小回收门槛后的轨迹尚未实测。

**同次旧规则观测**：`④ 命中缓存峰值` 达到 21248 token，输入峰值 21587，两者之比是 98.4%。
两个峰值未必来自同一次调用，不能把这个比值当成单次命中率；它也不能证明裁剪或压缩的缓存代价是否划算。
比较收益需要结合逐次调用的费用、延迟和后续输入量。

**长期记忆开着、两层都开的旧规则那跑，裁剪一次也没触发**（08-28 实测，同样 8000 预算 / 15 轮）：
`已清理` 整列是 0，旧报告的 `可回收量粗估` 报 `合计 3844 字符，其中最大两块 3356`，按峰值折算的下限是
2395。最大两块不等于最近两个循环，这几个汇总数不能还原当次候选的可回收量。上下文峰值也只有 11974，
远低于 08-25 那跑的 22048。当时还观测到工具调用构成变化：`flush_memory` 占掉了 t02/t10 的循环，
那两轮就少调一次 `search_knowledge`，
tool_result 的总量跟着掉；压缩又在 t04 就落了地、之后一直摁着，早期原文连同旧 tool_result 一起被删走。
判定给的是 UNCOVERED 不是 FAIL，裁剪那层代码这一跑压根没被验到。这也是旧规则的记录；删除比例门槛后
不能再按 2395 这个下限判断。**要单独覆盖裁剪，可以按上面那节关掉 `summary-enabled` 跑一趟**。

验完记得把预算改回去、把 `evictable-tools` 填回去。**「改回去」现在指的是 yaml 里那个 10 万，不是
120 万**——那个数本身还没定夺（见上文），别顺手在这一步把它当生产值确认下来。生产值该定多少不等于
「换了哪个模型」：先看那个模型的窗口，再把人设、工具 schema、本轮输出预留、字符折 token 的误差逐项
扣掉，剩下的才是这个数。不要照抄这里的调试值。

### 单会话排查

不想重跑对话、只想再看一眼某条会话的状态：

```bash
java -cp resources/regression/agent-memory/artifacts/classes \
  com.nageoffer.ai.ragent.initializer.AgentMemoryProbeMain \
  --suite-dir resources/regression/agent-memory \
  --session <会话ID>
```

它只读 `t_agent_state`，不发起任何对话。会把该会话的消息数、四类内容块数量、每块 tool_result 的
体量、逐条 usage 全部摊开。锚点默认取剧本里的 `anchor`，用 `--anchor <关键词>` 可以查别的词——
拿它查线上会话「为什么忘了某件事」也是成立的。

### 改剧本

`turns.properties` 一行一个配置，加轮次只要在 `turn.refs` 里追一个 ref 再补上它的键：

| 键 | 含义 |
| --- | --- |
| `anchor` | 全场锚点，判定「记不记得」全靠它。**必须是知识库里查不到的内容**，否则模型检索一下就答出来了，验的就不是记忆 |
| `turn.<ref>.session` | `main` 复用主会话，`fresh` 另开新会话 |
| `turn.<ref>.tier` | `short-term` / `mid-term` / `long-term`，三层都已实现，都是硬断言；写一个不在 `IMPLEMENTED_TIERS` 里的值才会记 PENDING |
| `turn.<ref>.text` | 真正发给 `/agent/v1/chat` 的问题 |
| `turn.<ref>.expect-any` | 回答里出现任意一个即算命中，`\|` 分隔；留空表示不判回答内容 |
| `turn.<ref>.expect-tool` | 期望调用到的工具。不命中记 UNCOVERED 而不是 FAIL——检不检索是模型自己的决定 |
| `turn.<ref>.forbid-tool` | 本轮不该调用的工具，调了即 FAIL。**「答案必须来自记忆」的轮次靠它判**：关键词问题里就带着，复述不算记住，重查一遍才是真没记住 |
| `turn.<ref>.purpose` | 报告里的说明文字 |

判定关键词只匹配正式回答，不匹配思考内容。模型「想到过」不算记得。

## 机制回归

剧本验「回答里记不记得」，验不了长期记忆的管道正确性——并发下整批拒不拒、在飞快照作不作废、
水位重不重叠、块顶到上限之后合并压不压得回来。这些只能从库上看，走另一个入口：

```bash
java -cp resources/regression/agent-memory/artifacts/classes \
  com.nageoffer.ai.ragent.initializer.AgentMemoryMechanismMain \
  --suite-dir resources/regression/agent-memory \
  --case all
```

`--case` 可以只跑其中几条，逗号分隔，如 `--case M1,M2,R5`；默认 `all`。

| # | 验的是 |
| --- | --- |
| M1 | 人工推高 revision 后提交 → 整批 CONFLICT，决策不落库、水位不动 |
| M2 | 人工推高水位后提交 → 同样整批拒绝（revision 拦不住的那个洞） |
| M3 | pending 只有一轮时 flush 照样执行，不被后台那道轮次门槛挡 |
| M4 | flush 判出 NOOP 之后水位照样推进 |
| M6 | 对话撤回后不再注入，且同一次调用里的后续推理已看到新视图 |
| M7 | 取代目标在仲裁之后才失效 → 只丢这一条，同批其余照写，抽取正常结到终态 |
| M8 | 抽取下界的两面：抹掉控制行重演首次使用，flush 后抽取区间必须从首条消息起（控制行由聊天入口在消息落库前预建，建晚一步首条就成「历史」永久漏抽）；再伪造一条早于建行的旧消息，第二轮抽取不许把它回灌进来 |
| M9 | 积压一批装不下：本次请求前造 45 条积压，flush 必须接着跑第二批罩住本次请求，不能跑完头一批就报「已更新」 |
| M10 | 积压超过三批：造 125 条，flush 跑满三批仍罩不住本次请求 → 只能报未完成；剩下的由轮次收尾的后台批接着消化 |
| R1 | 跨会话可见：一条会话里说的偏好，新会话开口就认得；块不许落进 `t_agent_state` |
| R2 | 撤回不复活：撤回后新会话没有，**再故意逼一次合并，仍然没有** |
| R3 | 改口之后注入块只剩新值，旧行退场并挂上后继 |
| R4 | 水位不重不漏：相邻两批的消息区间首尾严格递增 |
| R5 | 容量上界：灌超上限 → 合并压回去，压不动就淘汰旧条目；淘汰不许越过停手水位、FLUSH 分档殿后（本用例语料下不该淘到它；殿后是弱优先级不是绝对保护），撤回过的正文没被并回来 |
| R7 | 旧会话积压不覆盖新纠正：A 里随口说住杭州不整理，B 里改成南京并整理 → A 那句必须随 B 的整理按序处理掉、此后不再被第二批处理，回 A 闲聊两轮后生效集仍是南京，新会话答南京 |
| R8 | 删除之后旧会话积压不写回：同样的 A 积压，B 里先记住杭州再删掉 → 回 A 闲聊两轮后生效集里不许再冒出杭州，新会话答不知道 |
| R9 | 对话清空全部：记两件事后要求清空 → 生效集为空、那批结成 WRITTEN；清空后再说的照常记住，新会话认不出清掉的事 |

**这个 CLI 会直接写库**：造并发要改 `t_agent_memory_control`，R5/R2 要灌语料，M9/M10 要造积压消息。行为剧本不直接改库，但正常聊天仍会生成会话、消息和长期记忆。
每条用例跑完都把生效集还原到进场时的基线，假数据按 `99` 前缀物理删干净，M9/M10 的积压消息按 ID 删，所以用例之间互不污染，
也不动这个账号本来就有的记忆。中途 Ctrl-C 会跳过收尾，此时用 `--case` 单独重跑那一条即可，
它进场时会重新取基线。

**水位按用户不按会话**（2026-09-27 起）：一个用户所有会话里的消息按说话先后排成一条队，上一条用例没抽的尾巴、
这个账号平时聊天没抽的消息，都会混进下一次抽取。所以每条用例开场先等在飞抽取落定，再把这个账号的积压整片越过——
台账里插一行 `98` 前缀的 NOOP，**收尾不删**：删了水位就退回去，回归聊过的话会在这个账号下次真实聊天时被抽进长期记忆。
代价是这个账号跑回归之前还没抽取的消息从此不会进长期记忆，**建议给回归配一个专用账号**（改 `regression.properties`
的 `auth.username` / `auth.password`）。R9 会把这个账号的全部记忆清空，收尾的基线还原会把它们放回来。

判定里的 `UNCOVERED` 在这里比剧本套件常见：M1/M7 要在抽取在飞的那一瞬间改库，M4 要模型恰好判出
NOOP，逮不到就是这次没跑到那条分支，**不算回归，重跑一次通常就有了**。

**从某一条用例起、后面每条都报 `用例执行 抛出异常: java.io.IOException: closed`，先去服务端日志翻
模型供应商的状态码，别当回归查。** 模型账户欠费时供应商回 402，流式响应被中途掐断，回归台这头只看得到
连接被关，症状与代码无关却极像整片崩塌（2026-08-27 实测：M1 起前五条全绿——含当时还在的 M5，
编号口径见下文「回滚变红」，M6 第三问撞上
`status 402 | account balance is insufficient`，其后八条用例清一色这个异常）。判据是日志里的
`HTTP transport error during streaming`，充值之后原样重跑即可。

### R5 与 R2 需要把预算调下来

这两条都要求「注入块能被顶到上限」。上限是 `clamp(0.005 × context-window-chars, 1500, 6000)`，
`memory-capacity.properties` 的语料总共不到 2000 字符。**30 万是这个上限的分水岭**：`0.005 × 300000`
正好 1500，再往下这个比例就完全失效、上限恒等于下限 1500，语料顶得上去；120 万那档上限是 6000，
顶不上去——报告会给 `语料顶到上限门口 UNCOVERED`，合并那条路一次都跑不到。

**yaml 当前那个 10 万本身就在分水岭以内**（上限已经是 1500），所以这两条按现状直接跑就能覆盖；只有把
预算改回 120 万之后才要照下面压一遍。压到 30 万以内，重启再跑：

```yaml
agent:
  memory:
    context-window-chars: 8000   # 与验压缩/裁剪用的是同一个调试值
```

**服务端和回归台必须读到同一个数**。回归台默认从 `application.config` 指向的那份 yaml 读，所以
改 yaml 重启是最省事的做法。若服务是用 `--agent.memory.context-window-chars=8000` 这类启动参数
拉起来的，yaml 里还是生产值，就要另给回归台一份覆盖：

```properties
# resources/regression/agent-memory/artifacts/regression-9091.properties
application.config=<绝对路径>/bootstrap/src/main/resources/application.yaml
auth.username=admin
auth.password=admin
server.base-url=http://127.0.0.1:9091/api/ragent
agent.memory.context-window-chars=8000
```

```bash
java -cp resources/regression/agent-memory/artifacts/classes \
  com.nageoffer.ai.ragent.initializer.AgentMemoryMechanismMain \
  --suite-dir resources/regression/agent-memory \
  --config resources/regression/agent-memory/artifacts/regression-9091.properties --case R5
```

`--config` 里的键覆盖 yaml 派生出来的同名键。`server.base-url` 一并列出来是因为它默认取 yaml 的
`server.port`——本机同时开着 IDE 实例和验证实例时，不覆盖就会打到错的那个进程上去。

两处不一致不会报错，只会静默算错：回归台按自己那份数判断「顶到上限没有」，服务端按自己那份数决定
合并跑不跑，对不上的时候报告给的是 UNCOVERED 或莫名其妙的 FAIL。

**把预算调小会顺带缩小合并计划的输出上限，这条路上踩过一次**：合并的 `maxTokens` 一度直接取
`resolveMemoryMaxChars()`，1500 的块字符上限当成了 1500 token 的输出上限。条目多起来之后计划被截在
半途，日志报「合并输出解析失败」，偶尔还能被宽松解析出半份计划、组员 ID 缺胳膊少腿，提交侧照着
`成员不可用` 全组丢掉，最后只剩 `容量拒收`。计划体量跟**条目数**走，与块能存多少字符是两码事，
现在按 `16 × 条目数 + 目标水位` 派生。跑 R5 / R2 时若看到判定莫名 UNCOVERED，先去日志里翻这一行。

### 回滚变红

每条机制断言都要能被证伪，否则它只是在描述现状。加断言时按这个顺序做一遍：把对应机制注释掉
（比如把 `AgentMemoryRepository` 提交事务里的 revision 校验去掉）、跑一次确认 **FAIL**、再恢复、
再跑一次确认 PASS。只跑通过的那一遍，等于没验。

2026-08-27 按这个顺序把七刀过了一遍，记两条经验。下文点名的 **M5（在飞期间翻开关）与 R6（关闭窗口不补抽）
已随 08-28 删掉用户记忆开关一并移除**，上面的用例表里查不到了；这段照当时的实际编号留着，改写成「本来就没有」
等于把这次回滚练习的账目做假。

**一次只许断一处机制，断多了会互相盖住。** 首轮同时注释掉 revision 校验、flush 门槛豁免、快照刷新
三处，结果 M1/M5/M2/M6 全报 UNCOVERED——门槛豁免一断，flush 也被三轮门槛挡住，抽取根本建不起来，
另外几条赖以「逮住在飞抽取」的现场就没了。**断点之间的依赖不看代码是想不出来的**：这三处在调用图上
毫不相干，却共用「抽取能建起来」这一个前提。拆成两轮跑，M3 单独红，M1/M5 红而 M2 作为对照保持绿。

**M2 那次对照本身就是最好的证据**：revision 校验被注释掉之后 M2 仍然 PASS，判定语写着
`版本号 93 -> 93，全靠水位这一道拦下来`——这正好实证了「revision + 水位双校验缺一不可」不是
一句设计口号，两道门确实各拦各的。

**两处断点单拆开都变不红，机制是双保险。** `M7 指不着的那条被丢弃` 有两道各自够用的守卫：提交事务里
`survivors.containsKey` 那道预筛，和 `apply()` 里 `supersede(...) != 1` 那道条件 UPDATE（注释写的
「与条件 UPDATE 是同一个谓词」说的就是这件事）。只注释掉任意一道，M7 照样全绿——**两道都注释掉才红**。
这不是坏事，但意味着谁哪天顺手删掉其中一道，没有任何一条断言会拦他。心里有数即可，不必为此拆断言。

**三条断言原先在「验库」和「验注入块」之间说岔了，已经改掉：**

- `R3 注入块只剩新值` 读的其实是生效集，把注入整个关掉照样绿。已改名 `生效集里只剩新值`，
  另补一条 `新会话拿到的是新值`——另开会话问一句城市名，那句答案只可能来自块，注入一关就红。
  设计文档验收第 3 条要的本来就是后者。
- `M4 NOOP 抽取推进了水位` 原先按 `status == "NOOP"` 这个字面量挑台账行。状态一旦写错，那一行直接
  从视野里消失，报告反倒去怪「模型仍从这句里挑出了可记的东西」——**把自己的 bug 记在模型头上**。
  已改成认「结到终态且决策数为 0」，状态写错就明着报 FAIL。
- `R6 关闭期间那句没被记住` 无论判定是 PASS 还是 FAIL，印的都是那句「enabled_since 把关闭期间的消息
  挡在素材之外」。红着的时候印一句安慰话比不印还坏，已按分支分开写。

发现 R6 这条之后把 52 条断言整份扫了一遍，同样的毛病还有四处，一并改掉：`M2 版本号确实没变过`
（红着还印「全靠水位这一道拦下来」）、`M3 素材只有这一轮`（区间跨了不止一轮还印「这里只有 1 轮」）、
`R4 满四轮只结出一次抽取`（结出两条还印「不够再结一次」）、`M6 新会话里也不再注入` 与
`R1 新会话认得这条`（两个方向印同一句）。**判定语里凡是解释「为什么这说明机制生效」的句子，都只在绿的
那一支成立**，写的时候顺手就跟着 PASS 那条路想，红的那支没人复读一遍。加断言时把 FAIL 分支的话先写出来，
写不出来就说明这条断言自己也没想清楚在验什么。纯粹摊数据的（`describe(extractions)`、`X -> Y`）不在此列，
它们两个方向都是事实。

第六处是**扫完之后才露出来的**，方向还是反的：M1/M5 共用的 `尝试次数退回上一档` 把「没退回说明这次
CONFLICT 来自仲裁失败」无条件缀在句尾，绿着也印——报告里于是并排站着 `尝试次数 1 -> 0`（退回确实发生了）
和一句说它没退回的话。**静态读一遍抓不全这类毛病，得让它绿着跑一次、把判定语当文章读**：红的那支平时
见不到，绿的那支天天印在眼前却没人真读。跑完扫一眼判定列，句子和数字对不上的就是下一条。

**M2 那场比赛原先常输，病根在赛跑线程的固定延时。** 逮到在飞抽取之后统一等 `MUTATION_DELAY_MILLIS`
600 毫秒再动库，那个数是给 M1/M5 定的——它们改的是 revision，得等仲裁把生效集读完，改早了模型压根
没看见那条记忆。**M2 伪造水位没有这个前提**：它只要赶在提交事务读水位之前落地，越早越稳。实测建批到
结算可以短到 **826 毫秒**（仲裁判 NOOP 时一秒不到就回来了），再等 600 毫秒就骑在窗口边上，伪造行
落在提交之后，整条断言看着像回归其实一次都没逼到。已给 `Racer.start` 加了延时重载，M2 走
`NO_MUTATION_DELAY`，其余照旧 600（M5 删掉之后只剩 M1 与 M7 两处）。**加断言时先想清楚这条要的是「等仲裁读完」还是「抢在提交
之前」，两者的最优延时是反的。**

顺带记一条**没采纳的写法**：一度想给 M2 加个「伪造行是否赶在结算之前」的判据，输了就记 UNCOVERED
而不是 FAIL。它在把水位校验注释掉的那一跑上**直接把红吃成了绿**——判据本身只要有一点不准，藏起来的
就是真回归。方向错得很彻底：回归台宁可偶尔吵，也不能替被测代码打掩护。判据留在
`AgentMemoryProbe.forgedLandedBefore` 里只当诊断信息用，改延时才是治本的那一刀。

**`R5 块压回上限之内` 原先会替反压邀功。** 一条都没并成时块字符停在上限上，是提交侧「容量拒收」
把新内容全挡回去摁住的，跟受限合并没关系，这时候给 PASS 等于把另一层的功劳记在合并头上（实测那跑
`1474 -> 1500`，正好 100%，读起来却像压回来了）。已改成：越界一律 FAIL，没越界但两条腾位置的路子
（合并、淘汰）一条都没跑记 UNCOVERED，跑起来了才 PASS。`受限合并确实跑了` 那条**仍然是 FAIL 不是
UNCOVERED**——把 `memoryConsolidator.plan` 注释掉靠的就是它变红，降成 UNCOVERED 会把 R5 的回滚变红
整个丢掉。合并计划整份作废（组员在提交事务里被判 `成员不可用`）时它也红，那是真话：这一跑合并确实
没把块压回去。

**容量淘汰进来之后 R5 从 4 条断言变 6 条，`独立记忆一条没删` 那条口径也换了。** 旧口径是长期记忆定稿
第 9 条「不许因为空间不够删掉仍然有效的记忆」的直接编码，而淘汰恰恰要推翻它——不改的话新策略会被
报成回归。现在灌语料分两批：带独有关键词的那几条灌成 `FLUSH` 且排在最前，其余灌 `BACKGROUND`，于是
看护对象**既最旧又最该活**，来源分档一失效它们第一个没。三次回滚变红对应三条：

| 回滚掉什么 | 该红的断言 |
| --- | --- |
| `AgentMemoryRepository.evict` 里那句停手水位下限判断 | `淘汰没越过停手水位` |
| `evictionOrder` 里按 `FLUSH` 分档的那个 `sorted` | `FLUSH 分档殿后生效` |
| `evict` 里 `targeted.contains(row.getId())` 那道过滤 | 看 `块压回上限之内` 与台账 `decision_count`（本批决策指着的条目被淘掉，条件 UPDATE 落空，那条决策被静默丢掉） |

`淘汰没越过停手水位` 量的是**全程最低块字符**不是末轮的数：中途淘穿又被下一轮写回来，只读末轮看不见。
它红的时候先别急着认淘汰——合并同样会压低存量，去日志翻 `长期记忆容量淘汰` 那几行认人。淘汰一次都没
跑（合并就把位置腾够了）时它和 `容量淘汰确实跑了` 一起记 UNCOVERED。

**两条已接受的产品取舍（08-29 拍板，不是待修项，回归不为它们设断言）：**

- **容量拒收整批回滚，混合批里的 RETRACT 一并撤销**，重试耗尽后随整批 DROPPED——用户的「忘掉 X」在
  满库 + 单批净新增超过 `max - stop` 的窄窗口下会丢。flush 路径模型会收到失败文案不至于谎报，后台
  路径用户无感知。批次构成由仲裁决定，live 环境造不出确定性现场，所以只记录不设断言。
- **容量淘汰与用户撤回在库上同形**（失效且无后继），回归里 `evictedItems` 靠「灌入时还生效、如今失效
  且无后继」推断，仲裁自产的 RETRACT 混进来只能按正文认；线上审计唯一的区分手段是
  `长期记忆容量淘汰` 那几行日志。不加 `invalid_reason` 是明确决策（没有代码读者），这是它的直接代价。

**`R1 注入块没落进会话状态` 这条关掉注入是变不红的**（负向断言，不注入自然更不会落库）。它防的是
「把记忆写进 `context` → 随框架落 `t_agent_state` → 用户删了老会话还在注入」那条路，要证伪得真去写
`contextMutable()`。没为它造这个假路径，这里记一笔说明它的射程。

**`同一次调用里快照已刷新` 这条判不了，已经改成常驻 UNCOVERED。** 把 `MemoryFlushTool.refreshSnapshot`
注释掉重跑，M6 三条照样全绿。原因是结构性的：flush 撤回的那个事实，本轮就写在用户消息和工具结果里，
模型据此就能答「已经忘了」，用不着看注入块——实测块里明明还留着旧度数（日志 `结局: WRITTEN, 落库: 1`
证明撤回已在本轮落库、只是快照没跟着换），模型仍然一个字没提。反过来「记住」方向同理：要记的东西
本轮就在对话里。**两个方向都不产生可观测的回答差异**，所以别再想着换个问法把它逼红了。这道机制防的是
模型读到自相矛盾的块，价值是真的，但它落在回答通道之外，按项目一贯口径（「没有便宜度量就不假装有」）
如实记 UNCOVERED。

## 配置

`regression.properties` 里只有回归台自己的参数（账号、超时、重试）。服务地址、数据库账号和
`agent.memory` 三项开关全部从 `application.config` 指向的那份 `application.yaml` 读，回归台不另存
一份——报告里印的「配置阈值」必须和服务端正在用的是同一个值，否则整张校准表是假的。

例外是那几个派生比例：它们编译在 `AgentMemoryProperties` 里，yaml 中读不到，回归台顶上留了手抄副本
——短中期那几个在 `AgentMemoryRegressionMain`，长期那几个连同块名、块壳与抽取状态列表在
`AgentMemoryProbe`，**改了服务端那边这里必须同步**。手抄处都带着注记写明同源对象，照着找即可。

回归台读新配置键时，`resources/initializer/common/ApplicationYamlConfig.load` 必须同步把键搬过来。
只改一头不会报错，只会读到默认值——P1 踩过一次：`summary.*` 四个键没搬，校准表有一半是编的。

排查回归台自身报错时加环境变量 `RAGENT_REGRESSION_DEBUG=true`，会打印完整堆栈。
